# Pitfalls — where the original blueprint is wrong or incomplete

Each item: the trap, the fix, and the test that proves it. Several of these were confirmed by
spikes before writing this kit (marked **verified**).

## Task 1
1. **MCP SDK major version (verified).** `mcp` 2.x (current latest 2.3.0) replaced the low-level API (`on_call_tool=` constructor callbacks, `add_request_handler(method, params_type, handler)`, new runner). The 1.x pattern in the blueprint doesn't run on 2.x. → Pin `mcp>=1.27,<2`; verified on 1.30.0 in `docs/reference/mcp_stdio_spike.py`.
2. **The `@server.call_tool()` decorator swallows errors (verified).** It turns exceptions into `CallToolResult(isError=True)`. → Assign `server.request_handlers[types.CallToolRequest]` directly and raise `McpError`; this yields a real `{"error":{"code":-32602,...}}` frame.
3. **Rebinding `sys.stdout` isn't enough (verified).** C extensions, child processes, and code holding an early reference to the old stdout write to fd 1 directly. → `os.dup(1)` for the transport, `os.dup2(2, 1)` for everyone else, before other imports.
4. **Unknown tool code.** The blueprint says `-32601`. The MCP spec's own example for an unknown tool is `-32602` ("Unknown tool: …"); `-32601` is for unknown JSON-RPC *methods*. → `-32602` for unknown tools, let the SDK return `-32601` for unknown methods.
5. **Protocol error vs. tool error.** Malformed input → protocol error. Well-formed input that fails business logic (customer not found) → `isError: true`. Mixing these up is a common grading miss.
6. **`\d` matches Unicode digits in Python.** `CUST-١٢٣٤٥` passes `^CUST-\d{5}$` under Python `re`. → Use `[0-9]`. Also test a trailing `\n` (Python `$` matches before a final newline; Pydantic's Rust regex engine doesn't, but test it rather than rely on it).
7. **Strict float.** Pydantic strict mode accepts a JSON integer for a `float` field and rejects `"50"` and `true`. That is the right behavior for money; document it and test both ways. Add `allow_inf_nan=False` and a 2-decimal check.
8. **Echoing input in errors.** `ValidationError.errors()` includes `input` and `url`. Returning that in `data` reflects user input (and potentially PII) back. → Strip them.

## Task 2
9. **Notifications.** Requests without `id` get no response. A batch of only notifications → HTTP 202, empty body. `"id": null` is *not* a notification. Empty batch `[]` → one `-32600` error object.
10. **Unsigned base64 JSON "tokens" = anyone can be admin.** The blueprint accepts `{"role":"admin"}` base64. → Real path is HS256 JWT with `exp` + leeway; static and unsigned tokens only behind `CP_ALLOW_INSECURE_DEV_TOKENS=true` (off by default, warned at startup). This is literally the zero-trust point of the task.
11. **Token passthrough.** Forwarding the agent's `Authorization` header to the downstream MCP server is explicitly called out as an anti-pattern in the MCP security guidance. → Strip it; use a gateway-owned credential.
12. **Tool-name smuggling.** `" admin_reset_key"`, `"Admin_reset_key"`, zero-width characters. → Strict name regex + case-insensitive prefix check.
13. **Id collisions on a shared stdio downstream.** Two clients both send `id: 1` → responses get crossed. → Rewrite ids per hop and map back.
14. **Child stderr pipe filling up.** If the gateway spawns T1 with `stderr=PIPE` and never reads it, T1 blocks once the pipe buffer is full → "my agent hangs". → Drain stderr in a background task.

## Task 3
15. **A fixed 36-char holdback leaks (verified).** Emails can be up to 254 chars; spaced card numbers break the "hold to last whitespace" rule; `"...1283 0366."` mixes numeric and email-char classes. → Fixpoint tail hold-back, bounded by `max_hold`; property-tested in `docs/reference/redactor_reference.py`.
16. **Blueprint card regex** `\b(?:\d[ -]*?){13,16}\b` over-matches any long digit run and misses 17–19 digit PANs. → Candidate regex + Luhn + 13–19 digits.
17. **`X-PII-Redactions-Count` as a response header is impossible for a stream** — headers are flushed before the first byte. → Final `event: guardrail` SSE frame + audit log.
18. **Filtering "invalid" SSN ranges** (9xx area) would miss `999-01-4242` from the demo. → Fail closed; redact anything SSN-shaped.
19. **Proxy buffering.** NGINX/Envoy buffer SSE by default, killing TTFT even if your code is perfect. → `X-Accel-Buffering: no`, `Cache-Control: no-cache`; document the Envoy/NGINX config in TROUBLESHOOTING.
20. **Zombie upstreams.** Client disconnects but the upstream stream keeps generating (and billing). → `async with client.stream(...)`, handle `CancelledError`, test with a mock that records closure.

## Task 4
21. **aiosqlite + concurrent `BEGIN IMMEDIATE` on one connection** → "cannot start a transaction within a transaction". → `isolation_level=None`, an `asyncio.Lock` per connection around each transaction; `BEGIN IMMEDIATE` + `busy_timeout` for cross-process safety; test both.
22. **Request bigger than the whole budget** returns 429 forever. → 413 `REQUEST_TOO_LARGE`.
23. **Failing over on every error.** A 400 from primary will be a 400 from backup too. → Fail over only on 429 / 5xx / timeout / connection errors.
24. **Streaming failover.** Once the first byte is sent you can't switch providers transparently. → Timeout applies to time-to-first-byte; mid-stream failure → SSE error frame.
25. **`asyncio.wait_for` cancellation.** It cancels the inner task, but only if the provider code is cancellation-safe (no bare `except Exception` swallowing `CancelledError`). → Test that the mock observes cancellation.
26. **`asyncio.TimeoutError`** is an alias of builtin `TimeoutError` since 3.11 — catch `TimeoutError`.
27. **Reconcile must not move the timestamp**, or a long request gets a fresh 60s window.
28. **Storing raw tenant API keys** in SQLite. → Store sha256.

## Numbers to treat with care
29. The blueprint's cost and latency figures (model prices, "<3.5 ms total", "1,000+ concurrent streams per 2 vCPU", "~4 KB per stream") are unmeasured estimates, and some model names/prices in it may be wrong. Quote only numbers from `scripts/bench.py` on your machine, and say what hardware they came from.

## Discovered during build

30. **CRLF on Windows stdio (verified, phase 0, Windows 11 / Python 3.14 / mcp 1.30.0).** The spike's `io.TextIOWrapper(..., encoding="utf-8", write_through=True)` uses the default `newline=None`, which turns every `\n` into `\r\n` on Windows, so each JSON-RPC frame ends in `\r\n`. Lenient clients cope (`json.loads` ignores the `\r`); strict newline-delimited parsers don't. → Pass `newline="\n"` to the TextIOWrapper in `task1_mcp_server/__main__.py`; T1 tests should assert frames end in `b"\n"` and not `b"\r\n"`. Apart from that, fd isolation (`os.dup`/`os.dup2`) works the same on Windows: the stray `print()` and the raw `os.write(1, ...)` both landed on stderr.
31. **Starlette runs the bare-`Exception` handler outside user middleware (phase 0).** `ServerErrorMiddleware` is the outermost layer, so a pure-ASGI correlation middleware's `send` wrapper never sees the 500 response, and its contextvar has already been reset. → The middleware also stores the ID in `scope["state"]`; `errors.py` reads it from there and sets `X-Correlation-ID` on the envelope itself. Covered by `test_correlation_id_echoed_on_error_responses[...boom...]`. Tests that hit a 500 need `httpx.ASGITransport(raise_app_exceptions=False)`, because Starlette re-raises after sending the response.
32. **`ruff format` also formats Python code blocks inside Markdown (ruff 0.17, phase 0).** It rewrote the code blocks in `SPEC.md`. → `pyproject.toml` excludes `docs`, `prompts` and `*.md` from ruff.
33. **`int in IntEnum` raises `TypeError` on Python 3.11** (it only became a value check in 3.12). The project supports 3.11+, so `jsonrpc.make_error` looks the code up with try/except instead.
34. **Tooling on this machine.** `python3` is the Microsoft Store stub; the real interpreter is `python` (3.14.0). The `uv` install script (`irm | iex`) was blocked by a local policy, so uv 0.13.7 was installed with `python -m pip install --user uv` into `%APPDATA%\Python\Python314\Scripts`, which is **not on PATH**. Add that folder to PATH, or reinstall uv with the official installer, so that the plain `uv ...` commands in the README work.
35. **Unknown methods come back as `-32602`, not `-32601` (verified, phase 1, mcp 1.30.0).** `BaseSession._receive_loop` validates every request against the `ClientRequest` union *before* dispatch; a method outside the union fails validation and is answered `-32602 "Invalid request parameters"`. (Methods inside the union with no handler, e.g. `prompts/list`, do get `-32601` from `Server._handle_request`.) The spike didn't exercise this. → `task1_mcp_server.server.serve()` relays the transport's read stream and answers requests whose method isn't in `KNOWN_REQUEST_METHODS` (derived from the SDK's union) with `-32601` itself. Covered by `test_unknown_method_returns_32601`.
36. **The SDK logs raw request input to the root logger (verified, phase 1).** The same validation failure path calls `logging.warning(f"Failed to validate request: {e}")`, a multi-line pydantic dump that includes `input_value=` (raw arguments, i.e. potential PII), and the bare `logging.warning` triggers an implicit `basicConfig`. → `common.logging.configure_root_logging()` installs our JSON stderr handler on the root logger with `FirstLineOnlyFilter` (first line, ≤200 chars, no traceback). Covered by `test_malformed_params_do_not_leak_to_stderr`.
37. **The SDK's fallback for an unexpected handler exception is `ErrorData(code=0, message=str(err))`** — a non-standard code and a leak of the exception text. → The T1 `tools/call` handler catches everything that isn't `McpError`, logs it with the traceback to stderr, and answers `-32603 "Internal error"`.
38. **Bare `NaN`/`Infinity` tokens survive transport.** pydantic-core's JSON parser (used by the SDK) accepts them, so they reach the tool handler as floats; strict `float` with `allow_inf_nan=False` then rejects them with `-32602`. Tested both over the wire and directly on the model.
39. **`httpx.ASGITransport` does not run lifespan (phase 2).** Anything created in a FastAPI lifespan (the gateway's shared `httpx.AsyncClient`, mock counters) doesn't exist when tests drive the app in-process. → `proxy.create_app(settings, downstream=...)` attaches an injected `Downstream` immediately, and lifespan only builds the pooled client when none was injected. `mock_downstream.create_mock_app()` creates its state in the factory. Startup behavior (the dev-token warning) is tested by entering `app.router.lifespan_context(app)` directly.
40. **Ids are rewritten per hop on the HTTP path too (phase 2, design).** Matching downstream batch replies by the caller's id breaks on duplicate ids inside one batch, and it trusts the downstream to echo `"7"` vs `7` faithfully. → The gateway sends internal integer ids and restores the original id from its own slot. It is the same mechanism PITFALLS #13 needs for stdio. Covered by `test_duplicate_ids_in_batch_are_not_crossed` and `test_id_type_preserved`.
41. **`httpx.ASGITransport` buffers the whole response (verified, phase 3, httpx 0.28.1).** `handle_async_request` awaits the app to completion and collects every `http.response.body` part before it returns the `Response`. In-process wiring therefore can't show TTFT, incremental upstream consumption or client disconnect, on either hop (client→gateway or gateway→mock). → The T3 timing and lifecycle tests (`test_first_safe_chunk_yielded_before_stream_ends`, `test_gateway_never_reads_full_upstream_body`, `test_client_disconnect_closes_upstream`, `test_upstream_error_midstream_emits_sanitized_error_frame`) run the mock LLM and the gateway under `uvicorn.Server` on `127.0.0.1:0` as tasks in the test's own event loop. That is still no subprocess and no external network. Content and ordering tests stay on ASGITransport.
42. **How a client disconnect reaches the stream generator (verified, phase 3, uvicorn 0.54 / Starlette 1.10).** uvicorn advertises ASGI `spec_version: "2.3"`, and uvicorn's `send()` *silently returns* once the client is gone. For spec < 2.4, Starlette's `StreamingResponse` runs `listen_for_disconnect(receive)` alongside the body iterator and cancels the task group on `http.disconnect`. So the generator gets `CancelledError` at whatever it is awaiting, including a paused upstream read. For spec ≥ 2.4 servers, Starlette relies on `send` raising `OSError` instead. → `gateway._guarded_stream` keeps the whole upstream lifetime inside one `async with client.stream(...)`, logs `client_disconnected` on `CancelledError`/`GeneratorExit` and re-raises. The mock's `upstream_closed` event proves the upstream was closed within 1 s (`test_client_disconnect_closes_upstream`).
43. **Statement order hides whether `BEGIN IMMEDIATE` matters (verified, phase 4, SQLite via Python 3.14 / aiosqlite 0.22.1).** `reserve()` starts with the evicting `DELETE`, which is a write, so even a deferred `BEGIN` takes the RESERVED lock before the `SUM`, and the 4-process test passed with `BEGIN DEFERRED`. Mutation check: with `DEFERRED` *and* a read as the first statement, workers crash with `database is locked`. Two readers both try to upgrade to writer; SQLite returns `SQLITE_BUSY` at once instead of waiting, because waiting would deadlock, so `busy_timeout` can't help. With `BEGIN IMMEDIATE` and the same read-first order, the test passes 3/3. → Keep `BEGIN IMMEDIATE`: it makes correctness independent of statement order. Don't "simplify" it away just because the test still passes.
44. **mcp 1.x's stdio server does not accept JSON-RPC batches (verified, phase 5, mcp 1.30.0).** Writing `[{...tools/list...}, {...tools/list...}]` as one line to T1 gets no responses at all, only a `notifications/message` (level `error`, logger `mcp.server.exception_handler`). The 2025-06-18 protocol revision removed batching, and the SDK's stdio reader validates each line as a single message. → `StdioMcpDownstream` fans a batch out as individual lines over the same pipe and gathers the replies; the proxy's slot merge restores order. The reader ignores server notifications such as this one.
45. **A guardrail placed in front of failover hides the failure from the router (phase 5, design).** T3's stream wrapper turns any upstream exception into a sanitized `event: error` frame. Wrapped around a T4 provider, that frame would be the provider's *first byte*, so the router would treat a dead primary as a success and never fail over. → `integration/redacting_provider.py` pulls the inner provider's first chunk itself, outside the guardrail, so errors up to that point still propagate (`test_scenario_b_...` and `test_scenario_e_...` would fail otherwise). After the first byte, errors become the guardrail's error frame, which is all that can be done once headers are sent.
46. **The stderr drain runs with a stale correlation contextvar (phase 5).** The drain task is created when the child spawns, so `get_correlation_id()` inside it returns whatever was set then (usually nothing). → Each relayed T1 line is logged with `extra={"correlation_id": <the child's own correlation_id>}`, which `JsonFormatter` already prefers over the contextvar. Covered by `test_single_correlation_id_visible_in_all_hops`. A deterministic crash test also needs a seam: kill-then-call races with asyncio reaping the child (the call just respawns it). So `test_stdio_downstream_recovers_after_child_crash` holds the downstream's write lock to park a registered request, kills the child, then releases it.
47. **T1 drops in-flight requests when stdin hits EOF (verified, phase 6, mcp 1.30.0).** Piping a fixed file (`python -m control_plane.task1_mcp_server < handshake.jsonl`) gives a nondeterministic subset of replies: over five runs the last one or two requests (an invalid-params call, even a `ping`) were missing. Reading stdin to EOF ends `server.run()`, which cancels request handlers still in flight. Real MCP hosts keep stdin open, so they never see this, but a naive pipe check does, and it looks like a protocol bug. → Runbook and README commands keep stdin open (`(cat scripts/handshake.jsonl; sleep 1) | ...`); with that, every request is answered, including the `-32602`. A graceful drain on EOF in `serve()` would fix the root cause (candidate for the hardening phase).
48. **On Windows, connection refused on localhost takes ~2 s (observed, phase 6).** Pointing T4's primary at a dead port gives `X-Failover-Reason: connect_error` only after ~2.0 s per request (`curl -w %{time_total}`), not immediately as on Linux, because Windows retries the SYN before reporting `WSAECONNREFUSED`. That is still under the 3 s timeout, so the reason is reported correctly, but the latency is easy to misread as a slow primary. Documented in README (T4 standalone) and TROUBLESHOOTING §7.
49. **A forced flush could leak PII one character at a time (found in the phase 7 adversarial review).** When an unbroken run of email/number-capable characters grew past `max_hold` (256), the redactor cut at `len - max_hold` without regard to matches. With tokens arriving a few characters at a time, which is how LLMs stream, each feed pushed out one more of the oldest characters, so a card, SSN or email sitting at the front of the run came out **whole and unredacted** (`x…x4111111111111111x…x`, 300+ chars, fed per character). Large chunks hid the bug, because the whole match landed in the flushed prefix and was redacted there; the chunking property test only covered runs shorter than `max_hold`. → `StreamingPIIRedactor._extend_past_matches` moves a forced cut to the end of any email, SSN or card candidate that straddles it, so the match is emitted as `[REDACTED]`. That only ever emits *more*, so memory stays bounded. Covered by `test_t3_forced_flush_never_splits_pii` (16 cases).
50. **The SDK answers unparseable stdio frames with a log notification, not a response (verified, phase 7, mcp 1.30.0).** For bad JSON, invalid UTF-8, a lone surrogate (`"\ud800"` is valid JSON syntax, but pydantic-core rejects it), a message with an `id` but no `method`, or a batch, the stdio reader passes a `ValidationError` into the read stream, and `Server.run` replies with `notifications/message` "Internal Server Error". The caller waiting on its `id` hangs; behind the gateway that's a 30 s stall. Two further obstacles to answering it ourselves: `JSONRPCError.id` is typed `str | int`, so it can't hold `null`, and the stdio writer dumps with `exclude_none=True`, which would drop the id entirely. → `serve()`'s relay intercepts the exception and answers `-32700` (not JSON) or `-32600` (JSON, but not a request) with `id: null`, through `_NullIdError`, a `JSONRPCMessage` that serializes itself. This supersedes the "no responses" behaviour noted in #44: a batch line now gets one `-32600`. Covered by `test_t1_unparseable_frames_get_a_jsonrpc_error_response`.
51. **`httpx.Response.aiter_lines()` buffers a line of any length (phase 7).** It has no line cap, and `iter_sse` had no frame cap either, so an upstream that never sent a newline, or never sent the blank line ending a frame, grew one event without bound. That broke T3's O(`max_hold`) memory claim. → `sse.iter_lines()` is a bounded bytes→lines splitter (moved here from `redacting_provider`), and `iter_sse` raises `FrameTooLargeError` past `MAX_FRAME_CHARS` (1 MiB). `guard_events` turns that into the usual flushed tail plus a sanitized `event: error`. Covered by `test_t3_sse_parser_bounds_an_unterminated_frame`.
52. **`json.loads` is not RFC 8259 (phase 7).** It accepts `NaN`/`Infinity`, so the gateway forwarded non-JSON, and deep nesting (`[[[…]]]`, 100 KB) raises `RecursionError`, which isn't a `ValueError`, so it escaped as a 500 *before authentication*. → `common.jsonrpc.loads_strict()` rejects both as `ValueError`, and the gateway answers `-32700`, or 401 when unauthenticated. FastAPI's own body parsing already turns these into 400/422, so only the hand-parsed `/mcp` path needed this.
53. **Only `delta.content` was being redacted (phase 7).** Tool-call arguments (streamed in fragments, like content), `refusal`, content sent as a list of parts, and `logprobs` tokens all passed through with PII intact. "Put the SSN in the tool arguments" walks past a content-only guardrail. → `_ChoiceGuard` keeps one streaming redactor per (choice, field), with each tool call keyed by its own `index`, flushes them all before `finish_reason`, and drops `logprobs`, which repeats the text split at token boundaries and can't be redacted reliably. Non-streaming responses redact every string in `message`.
54. **`max_request_body_bytes` was only enforced on `/mcp` (phase 7).** FastAPI reads and parses the whole body before a route runs, and fields outside `messages` don't count toward the token estimate, so a 2 MB `padding` field was accepted, held in memory, and forwarded to the provider. → `common.body_limit.BodySizeLimitMiddleware` (pure ASGI) refuses an oversized `Content-Length` up front, and stops a chunked body at the limit by raising `HTTPException(413)` from `receive`, which FastAPI re-raises from body reading. It is installed on T3, T4 and the integration app's LLM route; `/mcp` keeps its own JSON-RPC-shaped 413. The token estimate now covers every message field as well.
55. **No deadline applied to a stream after its first byte (phase 7).** `request_deadline_seconds` only bounds time to first byte, which is right because generations can legitimately run long. But a provider that stalled mid-stream held the connection and the reservation forever (in-process), or up to the 60 s per-read timeout with no total bound (HTTP, trickling). → `stream_idle_timeout_seconds` (default 30 s) caps the gap between chunks in the router's relay; on expiry the client gets a sanitized `event: error` (`GATEWAY_TIMEOUT`), the upstream is closed, and the reservation settles to what was generated.
